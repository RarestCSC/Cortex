### 1.2 ⚠️ 按字面改成「空集」会引入 4 处新回归——这是我偏离字面指示的地方

你给的修复方向是「`accepts()` 的『端点与目录都没声明』分支返回**空集**而非三元组」。
我把字面版本实现出来并跑了测试，**它打破 6 条既有测试**，其中 2 条是乙/丙本轮的核心不变量：

```
---- test_responses_effort_gate_matches_the_chat_path_and_the_menu stdout ----
assertion `left == right` failed: cn:space-bunny   left: None   right: Some("high")
    （该用例紧接着断言 sends_thinking_effort() == expected.is_some()，
      即「菜单给档位 ⟺ 出站带上」——空集版本直接违反）
---- explicit_reasoning_metadata_overrides_model_name_in_responses stdout ----
```

**根因**：`(None, None)` 分支并不只服务于「网关闭默型模型」。我逐个查了目录解析
（临时探针，已删除），这条分支的真实覆盖面是：

|---|---|---|---|
| `cn:glm-5.3-flash` | `zhipuai/glm-5.3-flash` | ✅ `[low,high,max]` | 不受影响 |
| `gpt-6.1-sol` / `global:gpt-6-luna` | `openai/…` | ✅ | 不受影响 |
| **`zai-org/GLM-5.3-Flash`** | ✗（目录挂在 `siliconflow/` 下，而 `openai.rs` 的映射**把 provider 写死成 `"openai"`**） | ✗ | **菜单 3 档、出站 0 字节** |
| **`claude-sonnet-4`** | ✗（`None`） | ✗ | **同上** |

也就是说：**空集版本会把乙花整轮消灭的「UI 承诺自己不兑现的能力」，从一个模型扩散到一族模型。**
这与你要修的 bug 是同一个病，只是换了位置——所以我没有按字面执行。

### 1.3 实际采用的实现：只发明「词」，不发明「档位」

你要的两条验收标准是 **① Off 省略字段、② Max 不发 high**。下面这版两条都满足，且不产生新回归：

```rust
// formats/openai.rs，accepts() 的第三条分支
let own_word = own_effort_word(effort);          // Off ⇒ None，其余 ⇒ 自己的名字
...
(None, None) => own_word.is_some_and(|word| word == *level),
```

```rust
/// The word a level is named after, or `None` when the level has no word of its
/// own. `off` is the only one: it means "stop", which no vocabulary spells the
/// same way, and the near neighbours are all levels the user did not ask for.
fn own_effort_word(effort: ThinkingEffort) -> Option<&'static str> {
    match effort {
        ThinkingEffort::Off => None,      // ← 没有证据能表达「停」，只能说nothing
        ThinkingEffort::Low => Some("low"),
        ThinkingEffort::Medium => Some("medium"),
        ThinkingEffort::High => Some("high"),
        ThinkingEffort::Max => Some("max"), // ← 不再降级成 high
    }
}
```

| 场景 | 改前 | 改后 |
|---|---|---|
| 选 **Off**，端点与目录都没声明 | `"low"` ❌ | **不发字段** ✅ |
| 选 **Max**，同上 | `"high"` ❌ | **`"max"`** ✅ |
| 选 Low/Medium/High，同上 | low/medium/high | 不变 ✅ |
| 端点**已声明**词表（workbuddy 全部模型） | 走端点分支 | **完全不受影响**（一行代码都没碰）✅ |
| 目录有词表（gpt-6 / GLM / xAI） | 走目录分支 | 完全不受影响 ✅ |

关键性质：**菜单仍然兑现**。选 Max 就真的发 `max`（端点若不接受，走 G1「被拒→剥一次→落盘」），
而不是像三元组那样把 Max 悄悄换成 high。G1 的乐观发送对沉默型网关也仍然有效。

### 1.5 一个**同类但未修**的缺口（只报告，不改）

`Off → low` 不止发生在「无证据」分支，**目录有词表但没有「关」的词时同样发生**：


因为 `cn:glm-5.3-flash` 的目录词表是 `[low, high, max]`，`preferred = [none, minimal, off, low]`

### ③ 让 `gateway.py` 的 `/v1/models` 带能力字段 —— 不推荐

不在本仓库（`~/.cortex/free-lane/gateway.py`）。它还有个结构性问题：
free-lane 是**代理**，不是源站——它报出来的能力是**上游 OpenCode 的**，不是它自己的。
让代理替上游声明能力，等于把「B2 消费端点自报」这条优先级最高的证据源变成二手证据。

### 建议

**先 ①，后（或不）②。** ① 落地后 `oc-*` 自动拿到正确的档位**和**视觉，② 就没有存在理由了。

### 4.1 ✅ workbuddy 切换失败 —— 不是代码 bug

**症状**：GUI 里切到 workbuddy 报「无法切换模型 / Internal error」。

**根因**：`custom_wb2api.json` 用 `"api_key_env": "WB2A_API_KEY"`，而这个变量**只存在于 `systemctl --user` 的用户环境**，不在普通 shell 里。GUI 由普通 shell 启动 ⇒ 进程环境里没有该变量 ⇒ 切 provider 时构造 provider 失败。
实测证据：切之前 `tr '\0' '\n' < /proc/<serve-pid>/environ` 里**没有** `WB2A_API_KEY`；
从 shell 注入后（**只报长度 28，不打印值**）再测，`/proc/<pid>/environ` 里**有了**，用户复测**切换正常**。

**这正是 SUMMARY §6 第 6 条早已记录的已知问题**（原记录：「可行解只有注销重登」）。
本轮补充一条更省事的绕过：**从带该变量的环境启动 GUI 窗口**（`GOOSE_BINARY` + 注入变量），不必注销重登。

### 4.2 🔴 视觉开关「点了没反应」—— 真根因是**死 Tailwind 类**，不是 effect 依赖

**用户实测现象**（三条都排除了「状态被抹掉」这个假设）：

| 观察 | 含义 |
|---|---|
| 三个按钮（自动/开启/关闭）**初始全都不高亮** | JSON 里 `supports_vision: true` 是有值的，说明不是「值没读到」 |
| 点击后**完全没有视觉变化** | 不是「变了又弹回」，而是**根本没渲染出选中态** |

**根因**：组件用了 5 个**在主题里根本不存在**的 token 类。
`main.css` 的 `@theme inline` 只注册了 `background-*` / `text-*` / `border-*` / `ring-*` 四族（值由 `src/theme/theme-tokens.ts` 在运行时注入），
而组件写的是 **camelCase 的另一套命名**：`surfaceHover` / `textStandard` / `textSubtle` / `borderSubtle` / `borderStandard` / `iconSubtle`。
**Tailwind v4 不会为未注册的 token 生成任何工具类**。

实证（从 live dev server 取真正生成的 CSS，172KB）：

```
.bg-surfaceHover       0     ← 死类
.text-textStandard     0     ← 死类
.text-textSubtle       0     ← 死类
.border-borderSubtle   0     ← 死类
.bg-background-secondary 1   ← 存在
.text-text-primary     4     ← 存在
.bg-background-tertiary 1    ← 存在
```

所以选中态 `bg-surfaceHover font-medium text-textStandard` 实际只剩 `font-medium`，
11px 字号下几乎不可见 ⇒ **点击是生效的，提交也是对的，只是零反馈**。

**这推翻了交付文档对第 3 条 bug 的定位。** 丙的 G3（`useEffect` 依赖对象身份）修的是一个**真实但次要**的问题
——两个挂载点确实都在 render body 里现造 `initialData`，那个 effect 重跑也确实会抹掉点击；
但它**不是用户看到的那个症状的根因**。甲的 C4（协议层三态）同样与症状无关。
**三轮都没找到真根因，因为没有任何人在运行中的应用里点过一下**——这正是 §5-E 第 3 条要真机验收的原因。

**已修**：`CustomProviderForm.tsx` 里 15 处死类全部换成确实会生成的 token
（`text-textStandard`→`text-text-primary`、`text-textSubtle`/`text-iconSubtle`→`text-text-secondary`、
`border-borderSubtle`→`border-border-secondary`、`border-borderStandard`/`border-primary`→`border-border-primary`、
`hover:bg-surfaceHover`→`hover:bg-background-secondary`、`bg-surfaceHover`→`bg-background-secondary`），

否则又会变成「看不出变化」）。该文件现在**零死类**，`tsc --noEmit` 干净，4 条视觉用例仍全过。
