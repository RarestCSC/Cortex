# Cortex（基于 Goose）必要源码证据索引

> 2026-10-14 精简版。决策、现状、命令与测试结果只看 `refactor-plan.md`，此文不重复。
> 路径相对仓库根。Rust 行号为 2026-10-11/12 核对记录，**引用后端行为前必须重读源码**，索引不等于运行证据。无真实 HTTP reasoning 抓包。

## 0. 边界结论

- 现有 ACP 四维配置足够实现 UI；未为模型/思考入口改协议结构。只改 UI 不消除后端 wire/原子化/能力判断限制。会话配置、模型库存预览、全局新会话默认必须分离；后台回填为事实，用户请求目标不能冒充确认值。不做最近模型 UI，底层 recent-model 接口不在范围；完整供应商页/路由保留，Composer 的精简只影响可见入口。

## 1. 思考全链路（静态证据）

| 节点 | 源码范围与含义 |

| agent 应用 | `crates/cortex/src/agents/agent.rs:1194-1234`：先尝试 harness 接管；普通 provider 解析标准值并重建 |

| 配置 options | `acp/response_builder.rs:281-334,341-429`：provider/mode/model/thinking；harness 自带 string/label，unsupported 仅 off，普通非 reasoning 仅 off，GLM-5.3/Kimi-K3 三档，其余五档；currentValue 不携带来源标记 |

## 2. ACP/模型切换/配置状态（静态证据）

- `server/dispatch.rs:169-174,201-216`：provider set 有副作用，每次 set 构造 full options，**先通知后 response**，无 provider→model 批量原子事务。前端要缓冲中间态，不得假回滚。
- `server.rs:2428-2439,2562-2586`、`model_config.rs:21-34`、`cortex-provider-types/src/model.rs:17-24,261-281`：换模型/供应商继承旧会话设置再补全局；普通换模型不强制套全局 effort。
- `server.rs:218-219,2554-2578`：`goose` 是默认哨兵，不是库存 provider ID；实际 provider 从 sessionInfo 回读。UI 不应将 goose 写为全局具体默认。`response_builder.rs:166-209,248-278`：provider options 来自注册表，不等于全已配置；无 provider/model/库存时可能缺 configOptions，不能当不支持 reasoning。
- 前端入口 `ui/desktop/src/acp/{sessions,chatNotifications,configOptions,configOptionsStore,chatSessionController,chatSessionStore}.ts`。协议没有配置后端 revision，客户端操作 ID 不是后端版本；**超时不能当请求取消，不能自动重发未知结果的写操作**。尚需授权后专门核查：断线 uncertain 恢复、连接 generation、默认哨兵实际投影、跨窗口一致性；mock 通过不证明竞态闭合。

## 4.9 会话命名失效根因与可诊断性缺陷（2026-10-16，源码＋实测）

- **根因（静态＋实证，非猜测）**：`MessageContentBlock` 有独立的 `Thinking(ThinkingContentBlock)` 变体（`cortex-provider-types/src/conversation/message.rs:318-330`），而 `as_text()`（`:700`）**只对 `Text` 返回 `Some`**、`as_thinking()`（`:708`）才给推理块。故推理模型把答案放进 thinking 块时，`session_naming.rs` 原有的 `filter_map(|c| c.as_text())` 收集到**空串**；空串再被 `session_manager.rs:240-246` 的 `system_generated_name` 以 `if !name.is_empty()` **静默跳过写入**，随后 `system_generated_name_update` 仍发出一个 `title=""` 的通知，前端 `chatNotifications.ts:27` 的 `if (updatedName && ...)` 又判假 —— **全链路零日志、零 UI 更新**，标题永远停在 `new_session.rs:56` 的 `"New Chat"` 兜底。
- **定位方法（可复用）**：① 直接查 `sessions.db` 的 `name` 字段（不是看 UI 占位符）；② `state/logs/llm_request*.jsonl` 按 `session_name.md` 的特征句 grep，判断命名请求**是否发出**；③ `state/logs/cli/<日期>/*.log` 按 `"level":"WARN"` 统计，判断是否**报错**。三者组合才能区分「请求失败」与「结果为空」——本次结论是 28 会话 26 个 `New Chat`＋隔离态 79 个全部如此＋请求确有发出＋无 `Failed to generate session description` ⇒ 请求成功但结果为空。
- **修法（不猜子因，让取名永不为空）**：新增 `collect_title_candidates` 同时收集 text 与 thinking 两个通道，`normalize_whitespace` 复用原归一化，级联 `text → thinking → 首条用户消息 → warn!`；保留原有 `strip_xml_tags`／`extract_short_title`／`safe_truncate` 与全部既有测试不动，新增 3 例回归（thinking-only／双通道／空消息）。**未改** `strip_xml_tags` 的贪婪标签剥离——那是上游行为，改它有回归风险且未被证明是本例成因。
- **测试夹具类型修正（本次 clippy 暴露）**：`session_naming.rs:214` 在 `#[cfg(test)]` 内将 `rmcp::model::ContentBlock::text(...)` push 到 `Vec<MessageContentBlock>`，缺少 `.into()` 导致 E0308；现仅补转换，命名运行逻辑不变。旧仓库无该新用例，无法原样复跑，不声称旧仓库复现。编译检查与运行结果分开记录，见 plan §4.11。
- **可诊断性缺陷（独立问题，影响远大于命名）**：`ui/desktop/src/cortexServe.ts` 的 `onStderrData` 原来只把匹配 `isFatalError`（`panicked at`／`RUST_BACKTRACE`／`fatal error`）的行落 main.log，**所有 `warn!`/`error!` 级后端日志一律丢弃**，只在内存 `errorLog` 里、仅启动失败时吐出。这就是本次根因查了两轮的直接原因。现新增 `isBackendDiagnostic`（按 tracing 级别识别）落 `logger.warn`，`Logger` 接口加**可选** `warn?` 以不破坏既有实现与测试 mock。
- **另注**：`main.rs:20` 每次启动（含 `serve`）都调 `setup_logging`，但 `logging.rs` 是 `console: false, json: true` —— **后端日志进 `state/logs/cli/<日期>/*.log` 的 JSON 文件，不走 stderr**。故上述 stderr 通道与该 JSON 文件是两条互补路径，查后端问题应优先看 JSON 文件。
